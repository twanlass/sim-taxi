# The iOS app

The App Store build of Sim Taxi: the same web bundle, byte for byte, inside a native shell that
serves it over a custom URL scheme.

Everything native lives under `ios/`. Nothing under `src/` knows about it except through one flag —
`isNative()` in [`src/util/platform.js`](../src/util/platform.js) — and the three places that read
it are listed below.

| File | What it is |
|---|---|
| `ios/SimTaxi/AppDelegate.swift` | Entry point. One window, pre-scenes lifecycle. |
| `ios/SimTaxi/GameViewController.swift` | The `WKWebView` and its configuration. Wake lock, pause-on-background, orientation, status bar. |
| `ios/SimTaxi/BundleSchemeHandler.swift` | Serves `web/` over `simtaxi://`. **The load-bearing file** — see below. |
| `ios/SimTaxi/HapticsBridge.swift` | The `haptics` message handler. Taptic Engine feedback, which the web build has no route to at all. |
| `ios/SimTaxi/Info.plist` | Full-screen, no status bar, orientations, export compliance. |
| `ios/SimTaxi/LaunchScreen.storyboard` | One flat fill of `#DCEDF7`, matching `PALETTE.skyBottom`. |
| `ios/SimTaxi/Assets.xcassets/` | The 1024² app icon, generated by `tools/make-icon.mjs`. |
| `ios/SimTaxi/web/` | The build output. Generated by `npm run build:ios`, gitignored. |
| `ios/SimTaxi.xcodeproj/` | The project. Tracked — see [First-time Xcode setup](#first-time-xcode-setup) for the one line in it that is personal. |

## Why a custom scheme and not `file://`

This is the decision the whole port rests on, and it is not an optimisation — the obvious approach
does not work.

`WKWebView.loadFileURL(_:allowingReadAccessTo:)` is the documented way to load a bundled web app,
and it gives the page a `file://` origin. Four things break on that origin:

1. **ES modules fail the CORS check.** Vite emits `<script type="module">`. The game does not boot
   at all. Fatal and immediate — at least this one is obvious.
2. **`localStorage` throws `SecurityError`**, and this is the dangerous one.
   [`src/game/highscores.js`](../src/game/highscores.js) wraps every storage call in a `try` on
   purpose — Safari's private mode throws on write, blocked storage throws on the property access
   itself — and degrades to an empty table rather than killing a run over a saved score. Under
   `file://` that safety net becomes silent data loss: scores appear to save, every relaunch comes
   up empty, and nothing is logged anywhere.
3. **Root-absolute paths resolve to the filesystem root.** `vite.config.js` leaves `base` at `/`, so
   every emitted asset URL is `/assets/…`.
4. **Service workers never register.** Harmless — `src/main.js` skips registration in the shell
   anyway — but it rules out the fallback.

`BundleSchemeHandler` registers `simtaxi://` through `setURLSchemeHandler(_:forURLScheme:)`. WebKit
then treats `simtaxi://app` as an ordinary origin with its own persistent storage, module CORS
passes, and `/assets/…` resolves against the scheme root. No change to `vite.config.js`.

Three details in the handler are load-bearing rather than tidy:

- **Paths resolve from `URLComponents.path`, discarding the query.**
  [`src/game/recovery.js`](../src/game/recovery.js) answers a second WebGL context loss by reloading
  into `?safe=1` — the entire escape hatch for a device that cannot render the full budget.
  Resolving against the raw URL would look for a file named `index.html?safe=1`, 404, and turn a
  recoverable device into a permanently blank one.
- **`.js` must be served as `text/javascript`.** WebKit enforces the module MIME check strictly; an
  unknown extension falls back to `application/octet-stream` and the module is rejected before it is
  parsed. It reads as a blank page with one console line.
- **A missing `web/` is a `fatalError`.** It means the sync never ran, or — much more likely — the
  folder went into Xcode as a yellow *group* instead of a blue *folder reference*. A group flattens
  the hierarchy, so `assets/main-*.js` lands at the bundle root and every path 404s.

### Open question: does `localStorage` survive a relaunch?

Persistence under a custom scheme has been inconsistent across iOS versions. **Test it first**, per
the checklist below. If it does not hold, the fix is cheap: `createScores()` in
`src/game/highscores.js` already takes an injectable store, so a `UserDefaults`-backed one bridged
over `WKScriptMessageHandler` drops in behind the existing interface without touching the ranking.

**Half-answered, on the iOS 26.3 Simulator.** The write lands where a persistent one should — the
app's data container, under

```
Library/WebKit/<bundle-id>/WebsiteData/Default/<origin-hash>/…/LocalStorage/localstorage.sqlite3
```

— not under `Caches/` or `tmp/`, and it survives force-quit and repeated relaunches (checked by
reading the sqlite directly; the values are UTF-16, so `cast(value as text)` truncates them at the
first NUL and a `simtaxi.initials` of `AAA` reads back as `A`). So WebKit does grant `simtaxi://app`
an ordinary persistent origin rather than a per-session one, which was the thing in doubt.

What that does **not** prove is read-back, which is the half that has historically broken: a store
can be written, kept, and then not handed to the page on the next launch. Checklist item 4 is still
the test — and the cheap tell is the initials prompt, which pre-fills from `lastName(store)`. If it
opens on the initials you last entered rather than empty, the page read the store back.

## The native flag

`GameViewController` injects a `WKUserScript` at `.atDocumentStart` setting `window.__native = true`.

**Not a Vite mode.** `import.meta.env` does not exist in the inline `<script>` at the bottom of
`index.html`, which is one of the places that needs the answer, and it evaluates ahead of the module
bundle on purpose so it can catch a context-creation failure. More importantly a build mode means a
*second bundle*: two artefacts to keep in step and a Netlify deploy that can drift from the one in
the app. With a runtime flag there is one `dist/`, identical on the web and inside the `.ipa`.

Three places read it:

| Where | Behaviour when native |
|---|---|
| `src/main.js` (service worker) | Registration skipped. The bundle is already local, and a cache-first worker survives an App Store update — serving the old game to someone who just installed the new one. |
| `src/game/homescreen.js` (`isInstalled`) | Returns `true`. **Without this the App Store build shows a full-screen gate on every launch telling the player to install the game from Safari's share sheet** — a Guideline 4.2 rejection, holding the run behind it while it does so. `true` is the path an installed PWA already takes, so every downstream behaviour is already correct and already exercised. |
| `index.html` (error panel) | Says one sentence instead of painting a stack trace at `inset: 0`. Capture is unchanged and everything still accumulates into `window.__errorLog` for Safari Web Inspector — the build loses nothing diagnostically, it just stops printing it at the player. |

The debug panel needed no change: it has been opt-in behind `?debug`/`?settings` since the gear
button started overlapping the streak counter (`src/main.js`).

## What the shell adds

The shell **adds capability and does not adjust layout.** `index.html` and
[`src/util/viewport.js`](../src/util/viewport.js) already solve notches, home indicators, rotation
and cold-start viewport settling, against measurements taken on real hardware. So the web view is
pinned to the window's full bounds and left alone — `contentInsetAdjustmentBehavior = .never` in
particular, because the default insets by the safe area and would double up on the
`env(safe-area-inset-*)` padding the CSS already applies.

- **Wake lock.** `isIdleTimerDisabled = true`. There is no wake-lock code in `src/` because the Web
  Wake Lock API is not available in WKWebView — the web build simply cannot do this, and the screen
  dims mid-run. A fare has a 60-second clock and a player who is thinking is still playing.
- **Pause on backgrounding**, via `window.__taxi.pause.setPaused(true)` — the hook
  [`architecture.md`](architecture.md) documents, rather than a new channel. `setPaused` is
  idempotent and already respects `canPause()`, so backgrounding on the game-over screen is a no-op.
  Without it a fare clock drains behind whatever took the screen: WebKit stops firing
  `requestAnimationFrame` in the background, but the clocks are budgeted in *wall* time and
  `frame()` reconciles on the next tick, so the deadline is gone either way.
- **Haptics.** `UIImpactFeedbackGenerator`, via a `haptics` script message handler. The one
  capability here the web build cannot fake even badly: `navigator.vibrate` has never shipped in
  Safari on any platform, so on the open web this game has no route to the Taptic Engine — see
  [`src/util/haptics.js`](../src/util/haptics.js) for why there is no Android fallback either.

  The page posts an event *name*, not a duration or an intensity. Feedback styles are calibrated
  per device generation by Apple, so naming the event lets the native side pick the transient that
  is right on the phone it is running on; a page that posted "8ms at 0.7" would have hard-coded one
  model.

  Five events, in two groups. **The player did something** — these fire under a thumb already on
  the glass, so they are sharp and short, and every one is gated on the input being *accepted*
  (a refused tap or an ignored press stays silent, because a confirming buzz on a refusal says the
  opposite of what the screen is saying):

  | Event | Fires on | Transient |
  |---|---|---|
  | `pick` | a tap that re-aimed the taxi — rider, destination pin, package pin | `.light` |
  | `brake` | the brake going down, once per hold | `.rigid` |
  | `loco` | Loco Mode engaging | `.heavy` |

  **The world did something** — these land on a frame the player may not have been touching
  anything, so they carry weight rather than timing:

  | Event | Fires on | Transient |
  |---|---|---|
  | `parcel-in` | a package collected | `.medium` |
  | `parcel-out` | a package delivered | `UINotificationFeedbackGenerator` `.success` |

  Two of those choices are worth defending. `brake` is `.rigid` rather than something heavier
  because rigid is the hardest, shortest transient UIKit offers and it reads as a *mechanism
  engaging* rather than as an impact — the pedal should feel like it has a detent. And it fires
  regardless of the car's speed, unlike the skid mark it sits beside, because a control that
  answers only sometimes reads as a control that is broken. `parcel-out` is a notification rather
  than a fourth impact style because a notification plays a short *pattern*, which is what makes it
  read as a completion; it is also the only one of the five the player earned rather than merely
  caused.

  **A haptic is the one thing this game does that cannot be observed.** No pixel moves, nothing is
  logged, and the only witness is a thumb — so a dead bridge and a game that simply never fired
  look identical. `window.__taxi.haptic('loco')` in Safari Web Inspector separates them in one
  line. And it needs a real phone: there is no Taptic Engine in the Simulator or on any iPad, and
  on those the whole path runs correctly and produces nothing.
- **Deferred home-indicator gesture** on the bottom edge. The Loco Mode pill and the brake are both
  *hold* controls at the bottom of the screen, and a resting thumb there is exactly the gesture iOS
  reads as a swipe home.

## Build

```bash
npm run build:ios     # vite build, then tools/ios-sync.mjs copies dist/ -> ios/SimTaxi/web/
npm run push:ios      # the above, then build + sign + install to a paired iPhone over Wi-Fi
```

The sync mirrors rather than merges — the destination is emptied first, or the previous build's
hashed chunks accumulate forever. It drops three things and **says so on every run**: `lab/` and
`assets/lab-*.js` (the passing lab is a developer workbench with no route in from the game) and
`sw.js`. The exclusions are here rather than in `vite.config.js` deliberately: that file warns that
a `manualChunks` rule reaching into `src/` turns an import into a boot, and the web deploy wants the
lab.

Netlify is unaffected. It runs `npm run build` and publishes `dist/`, and never looks at `ios/`.

### Pushing to a phone

`npm run push:ios` ([`tools/ios-push.mjs`](../tools/ios-push.mjs)) does the five steps by hand
below, wirelessly, in about a minute. `--device <name|udid>` picks between paired phones,
`--release` switches configuration, `--no-launch` installs only. There is also a `/push-ios` slash
command that wraps it.

Two things in it are worth knowing rather than discovering:

- **It builds Debug by default**, which is the opposite of what a "push to my phone" script usually
  wants. `webView.isInspectable` is `#if DEBUG`, and Safari Web Inspector is the only console the
  game has on a device — a Release build installs and runs identically and tells you nothing when
  it doesn't.
- **It asserts the bundle layout** before installing, because a green build proves nothing about
  it. If `web/` lands flattened the app dies at `BundleSchemeHandler`'s `fatalError` on the phone,
  and the thing that breaks it is a project-file edit nobody remembers making. The check is one
  `find`; the fix, when it fires, is in "The bundle layout" below and not a rebuild.

A locked phone refuses the launch and only the launch — the install has already landed by then, so
the script says so and exits 0.

## First-time Xcode setup

**The `.xcodeproj` is tracked**, with the bundle-layout fix below already baked into it, so there is
no project to recreate. Two steps on a fresh clone:

1. Open `ios/SimTaxi.xcodeproj`, select the target, and set **Signing ▸ Team** to your own.
   `DEVELOPMENT_TEAM` is committed as one specific Apple developer account and is the only line in
   the file that cannot be shared; `PRODUCT_BUNDLE_IDENTIFIER` is `com.twanlass.simtaxi`, which
   another team will have to change too.
2. `npm run build:ios`. `ios/SimTaxi/web/` is gitignored — it is the build output — so a fresh clone
   has nothing for the scheme handler to serve and the app dies at `BundleSchemeHandler`'s
   `fatalError` until this has run once. `npm run push:ios` does it for you.

Two settings in it are deliberate rather than default. **Deployment target is 15.6**, not the
current SDK the template opens at — Xcode 26 will not go below 15.6, and taking the default
silently costs every device the shell was written to support. And `INFOPLIST_FILE` points at the
tracked `SimTaxi/Info.plist` rather than relying on the generated one, which is what carries the
full-screen, status-bar, orientation and export-compliance keys; there is no
`INFOPLIST_KEY_UIMainStoryboardFile`, so the app comes up on `AppDelegate` and not a storyboard.

There is **no Run Script build phase** running `npm run build:ios`, which means a stale bundle can
ship if you build in Xcode without syncing first — `npm run push:ios` is the guard against that.
Adding the phase is a fair trade for build time plus `node` on Xcode's `PATH`, but it also needs
`ENABLE_USER_SCRIPT_SANDBOXING` turned **off** (it is `YES` in the project today, as the template
leaves it): a sandboxed script phase cannot write into `ios/SimTaxi/web/`. Worth revisiting once the
shell stops changing.

`Assets.xcassets/AppIcon.appiconset/AppIcon-1024.png` is tracked, but if it ever goes missing the
asset catalog fails the build — `Contents.json` names it. `node tools/make-icon.mjs` regenerates it.

### The bundle layout, and why it is in the project file

The app bundle must contain `web/assets/main-*.js`, **not** `main-*.js` at its root. This is the one
setting that breaks the app when it is wrong, and it breaks it silently at runtime rather than at
build time: `BundleSchemeHandler` `fatalError`s on a missing `web/`, and every asset path 404s.

This is a **synchronized project** (Xcode 16+, `PBXFileSystemSynchronizedRootGroup` — the default
now), which means `ios/SimTaxi/web` is in the target automatically because it sits under the
synchronized root, and by default it is in there wrong. A synchronized group walks into every
subdirectory and copies the files it finds **flat**, so the whole bundle lands at the app root — the
old yellow-group failure, arrived at without anyone choosing it. The fix, committed:

```
/* Begin PBXFileSystemSynchronizedRootGroup section */
        …/* SimTaxi */ = {
                isa = PBXFileSystemSynchronizedRootGroup;
                explicitFolders = (
                        web,
                );
```

`explicitFolders` is the modern spelling of a blue folder reference: paths named there are copied
whole instead of walked into. Xcode exposes it on the folder's context menu, and writing it by hand
is safe — Xcode reads it back and shows `web` as a folder reference.

Note what does *not* work, because it looks like it should: adding `web` to the group's
`membershipExceptions` is accepted, changes nothing, and leaves you comparing two builds that are
byte-identical. The exception set only takes file paths.

If a project-file edit ever drops that list, don't trust the navigator — verify the built bundle:

```bash
find "$(ls -d ios/DerivedData/Build/Products/*-iphonesimulator/SimTaxi.app)" -name '*.js'
```

Every hit must be under `web/assets/`. `tools/ios-push.mjs` runs this assertion on every push for
exactly this reason: the break produces a perfectly green build and a dead app.

## Verification checklist

Run `npm run check` first — the web-side changes touch modules it covers. Then the fork itself,
which `npm run check` cannot see because it needs a browser:

```bash
npm run build && npm run preview &
node tools/native-smoke.mjs --url http://localhost:4173
```

That loads the same bundle twice, with and without the injected flag, and asserts every difference
in the table above in **both** directions — including that the Add-to-Home-Screen gate really does
still show on iOS Safari, which is the half that stops the fix from being "delete the feature".

Then, in the Simulator:

1. The game boots, the city renders, a tap routes the taxi.
2. Attach **Safari Web Inspector** (Develop ▸ Simulator ▸ Sim Taxi; `isInspectable` is DEBUG-only).
3. Console: `window.__native === true`; `navigator.serviceWorker.controller === null`; no
   `#dbg-toggle` in the DOM; the Add-to-Home-Screen gate never appears.
4. **Play a run to game over, enter initials, force-quit, relaunch — is the score still there?**
   This is the `localStorage`-under-a-custom-scheme question above, and it is the one result that
   can change the plan.
5. Load `simtaxi://app/index.html?safe=1` and confirm it serves rather than 404s — the `recovery.js`
   escape hatch depends on it.

On a real device, additionally:

6. Both orientations, cold start and after rotation. The HUD clears the Dynamic Island and the home
   indicator; no strip of bare sky at the bottom.
7. `?diag` for draw calls, triangles, drawing-buffer size and the granted `antialias`/`samples`.
   Current defaults are DPR cap 2, MSAA on, a 2048 shadow map and the half-res SSAO, with **no iOS
   tiering at all** — every iPhone gets the full budget. Do not pre-emptively turn it down:
   `recovery.js` has a ladder and `?safe`/`?msaa`/`?shadows`/`?dpr`/`?ao` bisect on-device without a
   rebuild.
8. **Five simultaneous WebGL contexts** — the main renderer plus the four HUD chips
   (`game/tutorial.js`, `riderfinder.js`, `taxifinder.js`, `cargochip.js`). iOS is stricter than
   desktop here and evicts the oldest. This is the most likely thing to bite; the fix if it does is
   to share one offscreen renderer across the four chips.
9. Take a call or pull down a notification mid-fare and confirm the run pauses.

## Still to do

Not built yet, roughly in value-for-effort order:

- **More haptics.** The bridge is in (see above) and carries five events. What is left is the
  *fare* loop — a rider's pickup and drop-off — plus the two failures, the bust and a collision.
  The fare pair is the interesting one: it wants to feel like `parcel-in`/`parcel-out` without
  feeling identical to them, since a fare is the main loop and a package is an errand, so they
  should not simply reuse those two names. Each is a `haptic()` call at the site that already
  knows it happened plus a case in `HapticsBridge.swift`; the thinking is in which transient
  belongs to which, not in the plumbing.
- **Game Center leaderboards.** The strongest Guideline 4.2 cover there is, and
  `highscores.js`'s injectable store is the seam it slots into. Keep the local top-5 and submit in
  addition.
- ~~**Audio.**~~ Done — see [audio.md](audio.md). Synthesised Web Audio, no sample files, so the
  zero-external-assets line holds. `AppDelegate.configureAudioSession()` sets `AVAudioSession` to
  `.ambient` so it mixes with the player's music rather than stopping it, and
  `GameViewController`'s empty `mediaTypesRequiringUserActionForPlayback` is what lets a sound fire
  on a frame nobody touched the screen.
- **App Store submission**: a privacy policy URL (required even though the app collects nothing —
  it makes no network requests at all, so the nutrition label is "Data Not Collected"), age rating,
  and screenshots. `tools/shoot.mjs` can render the required sizes — 6.9" iPhone at 1320×2868, and
  13" iPad at 2064×2752 if iPad ships.
